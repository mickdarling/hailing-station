# Provider turn-context dispatch

Implementation prerequisite #145, part of #141 and #132. `ProviderInputCoordinator.Configuration.deliveryMode` defaults to `legacy`; `contextual` explicitly requests the optional `ProviderContextDelivering` capability registered with the target's adapter. Unsupported contextual delivery fails before any adapter write or confirmation consumption, with no legacy fallback.

Both modes share `HailHost`'s existing guarded dispatch implementation: sanitization, the fresh target listing, exact binding, policy and confirmation reload, lockdown, per-line rate-limit admission, and cancellation. The contextual adapter receives the coordinator's immutable proposed context alongside each sanitized literal line and exact opaque adapter binding. A context's provider must identify Registry's adapter kind. Adapters must check that the target still has the supplied exact binding immediately before side effects, including any later commit/Enter action; the host listing cannot replace that adapter check.

Only complete dispatch registers `sent`. Receiving a context does not prove provider acceptance, output, lifecycle completion, or successful real-world effects. Multiline dispatch carries the same proposed context on every line. Partial writes preserve known delivered lines and never register a successfully sent turn; independently emitted output for such a proposed context remains explicitly unknown/unassociated. Final text does not complete a turn.

Cancellation admission still commits the first attempt at the single post-policy-reload checkpoint before consuming confirmation. Cancellation observed there preserves the token. After that checkpoint the first attempt may proceed; completed noncooperative writes retain sent evidence, and cancellation before later lines preserves partial evidence. Contextual capability resolution occurs before that checkpoint and before confirmation consumption.

Contextual input capability is separate from capture permission. An allowed input may dispatch with `capture: false`. This code starts no observation lease, grants no capture authority, owns no output task, and publishes nothing to the listener, manual reply endpoint, or mobile wire. #141 must independently acquire and revoke capture permission against the exact binding, own the observation lease/task, bound and reconcile early output, and cancel upstream work on every exit. Captured text must remain host-local until authenticated confidential delivery and output disclosure policy exist.

`ProviderContextDispatchTests` exercises the real guarded host path, including unsupported capability with an unconsumed valid confirmation, binding/provider mismatch, policy reload, sanitization, tiers, rate-limit, lockdown, and legacy compatibility. `ProviderContextCoordinatorTests` uses a synthetic adapter which emits accepted, user-visible text and explicit finish from the context it received **before** dispatch returns. The test, not a production host driver, owns the synthetic lease and retains/retries those real fixture events after successful registration. Failed partial input leaves its fixture output unassociated. A separate test proves contextual input does not acquire observation when capture is denied.

These tests use invented labels and text. There is no real tmux, Codex, live private-session capture, LLM, mobile correlation, physical-device, or TestFlight proof. Source version advances to 0.1.12; no build is uploaded or installed. #141, #132, #94 and #133 remain open.
