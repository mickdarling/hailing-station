## Reading the inventory

- **Definition and read:** file:line references identify declaration/parser/default/validation and consuming code. `:N` continues the preceding filename. Each section states its repository and abbreviations. Constraints describe what code enforces, not a recommended slider range. “No bound” means the UI/backend needs a deliberate validation decision, not unlimited safe operation.
- **Defaults and live values:** code/decoder defaults, absent sections and source-only initializer defaults are distinct. A safe on-disk scalar is reported where available; private addresses, target identities, enrollment/name lists, paths and secrets are withheld. Installed app preferences, running child state and process environments were not inspected. Unknown does not mean default. A JSON bool observation is not runtime proof.
- **Changer:** owner, app, admin and dev are recommended future roles. Producer/app denotes a programmatic per-invocation option under existing delivery authority, not a new right for a session to edit settings. App-generated opaque IDs, generations, transport invariants and system-supplied inputs should be visible but not arbitrarily editable. No current remote authentication capability is implied.
- **Activation:** immediate owner mutations, policy admission refresh, next job/renderer, fresh RightyO child, host restart and app/audio-owner recreation are different. Listening off/on only applies a setting when that path really reconstructs its reader. Do not use a hidden toggle as a substitute for an activation receipt.
- **Scope:** ordinary transient view presentation (for example whether a sheet is open), injected closures/test clocks, generated request tokens and fixed protocol/safety invariants are not new user preferences. Operational arguments are included explicitly as actions/profiles. Unsupported schema keys and proposed #1124 fields are never described as current working settings.

The future product must expose every supported entry below through **all three apps**, including Advanced and typed operation/profile forms, subject to role/capability and system restrictions. Sensitive actions need the same authorization as sensitive settings writes. The design's catalog coverage requirement prevents new file-only settings.

### Policy and target authority

`policy.json` lives beside host.json under `HAIL_CONFIG_DIR` or `~/.config/hail`. The directory must be owner-private (0700); regular file 0600, owner-owned, non-symlink; max 1 MiB (`Sources/HailDaemonKit/Policy/PolicyFile.swift:108`, `:117`). It is currently unsigned. Invalid or unknown keys fail closed. `TargetPolicy`'s initializer defaults do **not** make `tier`, `capture`, or `binding` optional in JSON: decoding requires all three (`Policy+Codable.swift:86`).

Policy refresh is **live at authority/admission boundaries**, not a periodic GUI observer or restart requirement: `Sources/HailDaemonKit/Daemon/HailHost.swift:371`, `:426`, `:446`, `:564`; `Sources/HailDaemonKit/Listener/WebSocketListener+SessionUpdate.swift:34`. Changes invalidate held confirmations/reply permits rather than silently authorizing old work. The future UI should wait for effective revision acknowledgment; reading the new file is insufficient proof that a previously admitted activity adopted it.

### Named routes and note destinations

The daemon loads the configured route/destination files at startup. Separately, `haild reply --say` loads the **standard** `routes.json` beside policy for a spoken source-name prefix on each invocation (`Sources/HailDaemonKit/Input/VoiceRoutes+Label.swift:6`, `:13` → `Sources/haild/ReplyCommand.swift:317`). That per-reply label lookup is not the daemon's configurable `--voice-routes` path; configuring a different path can therefore split the two views. Label changes can affect the next reply while input routing still needs restart. No existing app route-name editing API was found in this snapshot. A routes file names targets but grants **no policy permission**. These settings need owner authority even when exposed under Targets from every platform.

### Ownership and activation

`Sources/haild/ReplyCommand.swift:448` passes the calling CLI environment to each owned renderer. `Sources/HailDaemonKit/Provider/OwnedReplyRenderer.swift:414` copies that environment, forces `VBSAY_NOPLAY=1`, `VBSAY_STDOUT=1`, and an owned `VBSAY_OUT`, and supplies `VBSAY_CHUNK=160` only when absent. Thus a new ordinary reply sees its caller's new environment; changing a shell variable does not change a running daemon or already started renderer. Session-update speech captures the daemon environment when `OwnedSessionUpdateSpeechRenderer` is constructed (`Sources/HailDaemonKit/Notify/SessionUpdateSpeech.swift:19`, read at `:28`); current deployment/environment edits therefore need a daemon restart for this path. Coaching captures a supplied environment in its local renderer factory (`Sources/haild/CoachingSpeechRenderer.swift:68`). No listening toggle reloads these external environment values. All values below take effect on a **new renderer process**, with daemon restart where its cached environment is the source; rendered/queued audio does not change retrospectively.

**Proposed changer** is a design permission, not a claim that these settings are currently remotely writable. ### Per-target voice mapping (#1124): absent, proposed

At the pinned HS source, `ReplyOptions.apply` accepts no `--voice` (`Sources/haild/ReplyCommand.swift:78`), and its renderer is supplied only text, output root and caller environment (`:447`). A spoken route label is applied via `VoiceRoutes` (`:317`); a named voice **route** is a destination/label mapping, not a synthesis profile mapping. The target→voice map, guaranteed host default, doctor display, and allowlisted per-reply override requested in [#1124](https://github.com/mickdarling/hailing-station/issues/1124) remain design work. Do not list an invented live map or claim that the host already prevents fallback to the renderer's built-in profile.

The [2026-11-13 requirement on #1124](https://github.com/mickdarling/hailing-station/issues/1124#issuecomment-6862959360) additionally requires one persistent map for **targets and update types** (direct replies, proactive updates/update speech, status-only lines), with JARVIS default/coordination and FRIDAY status-only lanes. It requires the host to override/remove silent caller-environment selection, allow only explicit host-allowlisted audited overrides, preserve choices across restarts, show the effective map, and warn/fall back only to a documented default when a profile is missing. Those are requirements, not source behavior at the pinned baseline.

Proposed settings registry entries: host reply default profile, per-target inherited/explicit profile, per-update-type lane profile, profile allowlist, per-profile supported speed/EQ controls, and explicit one-reply persona override. Every app presents and can edit the same approved host capabilities; profile availability/engine support comes from the host. Ordinary untrusted reply-producing sessions must not obtain general configuration authority merely because legacy `VBSAY_PROFILE` could affect their renderer environment.
