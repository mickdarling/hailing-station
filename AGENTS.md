# Hailing Station agent instructions

Read README.md, CONTRIBUTING.md, and the relevant issue/design documents before implementation. Issues are the work records; changes use issue-linked PRs. Preserve the Apple-first, audio-first, provider-neutral architecture and distinguish proposed behavior from shipped or physically validated behavior. Never commit private endpoints, identities, transcripts, recordings, credentials, signing material, or generated build products.

## PR-shape: mandatory preflight and error handling

Read `scripts/pr-shape.py` and `.github/pull_request_template.md` **before creating any PR**, not only after CI fails. The checker is authoritative; do not rely on a remembered format. See CONTRIBUTING.md for the maintainer workflow.

1. Identify an **open issue** bearing `type:feature`, `type:spike`, `type:chore`, or `type:epic`. The first spec reference in the PR body must be `Part of #N` or `Closes #N` for that issue, not a PR number. Use `Part of` for incomplete parent work.
2. Count production files using the checker's exact exclusions and rename handling. The limit is four; tests/docs are excluded as specified by the checker. Split oversized changes. Do not use `bootstrap` to evade the limit. Check security-critical paths and apply required labels intentionally, without repeatedly toggling labels to force runs.
3. Run the applicable verification and spec traceability. Record exact commands/results, distinguishing synthetic tests, simulator builds, and physical-device proof. Do not use `trace: partial` to conceal a missing test; name real deferred expectations.
4. Finish intended commits before requesting independent review. Compare local `git rev-parse HEAD` with `gh pr view N --json headRefOid`; use the full **40-character** current remote head, never a short hash or merge/base SHA. Every subsequent push invalidates old exact-head approval and needs fresh review.
5. An initial draft awaiting review can legitimately fail the review-record portion of PR-shape. Clearly state this expected blocker in the PR and status report. Keep review status separate from completed `Round N:` verdict records. Do not fabricate `APPROVE` or `REQUEST CHANGES` to make a pending/failed/skipped/quota-limited review look completed. Smart review selection is not proof of review.
6. Once a real independent review completes, inspect all findings and exact-head evidence. Fix valid findings, verify changes, and request a fresh review after any push. Only then prepare the truthful completed body line `Round N: APPROVE ...` (or the actual verdict), naming reviewer, reviewed head, evidence, and resolutions. When a second key is required, publish its comment before updating that body record as described below. A latest `REQUEST CHANGES` blocks completion.
7. For `security:critical`, post a **new top-level PR comment** whose first line is exactly `## Review record (independent second key, round N)`, replacing N with the actual round. It must document a genuinely independent completed review and include its approving verdict and `head: <full 40-hex current SHA>`. Its first parsed verdict must be the actual approval, not a quoted old rejection. The checker uses the newest matching comment, not an old approval or a body-only record. Preserve history rather than editing a stale approval to claim it covered new code.
8. After posting the genuine second-key comment, make a **meaningful body update** containing its actual evidence link and the completed round record. Initial PR-open checks may have run before the comment existed; publishing that comment alone does not trigger PR-shape. Reapplying an identical body can be a no-op: success from `gh pr edit` is not proof that GitHub queued an edited-event run. Run `GITHUB_REPOSITORY=mickdarling/hailing-station PR_NUMBER=N python3 scripts/pr-shape.py` locally, then inspect the newest actual GitHub run and required checks: verify the run follows the meaningful edit, the reviewed PR head is still current, and statuses/conclusions belong to that head rather than an older run. A privileged base-branch workflow run may identify its base SHA, so confirm the PR's full head separately. Keep missing reviews honestly pending. Mark ready/merge only with actual reviews and passing protections; never bypass them.

**On any PR-shape failure:** read the exact diagnostics and latest run log; classify source count, spec state/label, review verdict, security label, missing second key, stale head, or a missing edited-event run. Fix only the cause. A metadata-only repair uses a meaningful comment/body update, not a new source push that invalidates review again. Do not toggle labels to manufacture a run. Rerun once after a meaningful correction; do not repeatedly poll or retry an unchanged review/service failure. Report the blocker and required next action accurately. A passing string parser is not a substitute for actual independent review or a passing current GitHub check.

Keep TestFlight marketing/build identifiers advancing under the project versioning policy. Do not upload or replace installed builds unless that delivery is in scope. Host-local groundwork is not a live captured-output round trip.
